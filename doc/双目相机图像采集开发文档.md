# 双目相机图像采集开发文档

本文档记录当前 Luckfox Pico Ultra W + USB UVC 双目相机的图像采集方案、板端验证命令和后续接入 `stream-sever` 的开发路线。

## 当前硬件结论

当前双目相机不是 MIPI CSI 传感器，而是 USB 2.0 UVC 摄像头。

相机规格：

```text
型号: HBVCAM-4M2214HD-2 V11
接口: USB 2.0
驱动: Linux UVC / uvcvideo
输出格式: MJPG / YUYV
推荐采集: MJPG 1280x480 30fps
备用采集: YUYV 1280x480 10fps
```

板卡规格：

```text
板卡: Luckfox Pico Ultra W
系统: Linux 5.10.160
USB 摄像头节点: 不固定，需运行时识别
```

注意：Luckfox Pico Ultra / Ultra W 的 USB-A 和 USB-C 不能同时作为 USB 数据通道使用。

```text
USB-C 有供电  -> USB 通道切到 USB-C
USB-C 无供电  -> USB 通道切到 USB-A
```

因此使用 USB-A 外接摄像头时，不能用 USB-C 给板子供电。需要使用外部 5V 供电、POE 模块或其它独立供电方式。

## 板端网络和 NFS

当前板端以太网常用配置：

```bash
ifconfig eth0 192.168.5.9 netmask 255.255.255.0 up
ip route add 192.168.5.0/24 dev eth0 src 192.168.5.9
route add default gw 192.168.5.1
```

虚拟机 IP：

```text
Ubuntu VM: 192.168.5.11
Luckfox:   192.168.5.9
```

NFS 挂载：

```bash
mkdir -p /mnt
mount -t nfs -o nolock 192.168.5.11:/home/xikao/object-detection_system/nfs_rootfs /mnt
```

如果板端 `ifconfig` 已显示 `eth0` 有 IP，但 `ip route` 为空，需要手动补路由：

```bash
ip route add 192.168.5.0/24 dev eth0 src 192.168.5.9
```

这条命令表示：访问 `192.168.5.0/24` 网段时，从 `eth0` 发包，并使用 `192.168.5.9` 作为源地址。

## USB 摄像头枚举验证

插入 USB 摄像头后，查看内核日志：

```bash
dmesg | grep -iE "usb|uvc|video" | tail -100
```

正常应看到类似：

```text
usb 1-1: new high-speed USB device using xhci-hcd
uvcvideo: Found UVC 1.00 device USB Camera (1bcf:0b15)
input: USB Camera: USB Camera ...
```

查看 USB 设备：

```bash
lsusb
```

查看 V4L2 设备：

```bash
v4l2-ctl --list-devices
```

正常应看到：

```text
USB Camera: USB Camera (usb-xhci-hcd.0.auto-1):
        /dev/video0
        /dev/video1
        /dev/media0
```

注意：`/dev/video*` 编号不是固定的。摄像头曾经出现过 `/dev/video21`，重新插拔后又变成 `/dev/video0`。程序不能写死节点号，应根据设备名称或能力自动识别。

## 采集能力确认

查看摄像头信息：

```bash
v4l2-ctl -d /dev/video0 --info
```

正常关键信息：

```text
Driver name: uvcvideo
Card type: USB Camera: USB Camera
Capabilities: Video Capture, Metadata Capture, Streaming
```

查看支持格式：

```bash
v4l2-ctl -d /dev/video0 --list-formats-ext
```

当前相机支持：

```text
MJPG 1280x480 30fps
MJPG 3840x1520 30fps
YUYV 1280x480 10fps
YUYV 640x480 30fps
```

推荐实时采集：

```text
MJPG 1280x480 30fps
```

## 采集测试命令

采集 MJPG 拼接双目图：

```bash
v4l2-ctl -d /dev/video0 \
  --set-fmt-video=width=1280,height=480,pixelformat=MJPG \
  --stream-mmap=3 \
  --stream-count=100 \
  --stream-to=/tmp/cam_1280x480.mjpg
```

检查文件：

```bash
ls -lh /tmp/cam_1280x480.mjpg
```

采集 YUYV 原始帧：

```bash
v4l2-ctl -d /dev/video0 \
  --set-fmt-video=width=1280,height=480,pixelformat=YUYV \
  --stream-mmap=3 \
  --stream-count=30 \
  --stream-to=/tmp/cam_1280x480.yuyv
```

YUYV 文件大小约为：

```text
1280 * 480 * 2 * 30 = 36,864,000 bytes
```

## 图像数据形态

该双目相机输出的是左右拼接图像：

```text
1280x480 = 左目 640x480 + 右目 640x480
```

客户端或算法侧可以按宽度中线拆分：

```text
left  = frame[:, 0:640]
right = frame[:, 640:1280]
```

如果使用 `3840x1520`：

```text
left  = frame[:, 0:1920]
right = frame[:, 1920:3840]
```

## stream-sever 当前状态

当前 `stream-sever/src` 主要仍是原有 RKMPI 链路：

```text
SimpleIPC: VI -> VPSS -> VENC -> H.264 stream
```

这条链路面向 MIPI/RKISP 摄像头，不会直接读取 USB UVC `/dev/video0`。

因此当前 `stream-sever` 可以编译，但不能直接用于该 USB 双目相机。后续需要新增一个 `UVC/V4L2 producer`。

## UVC Producer 开发目标

目标是在 `stream-sever/src/media_producer/` 下新增 V4L2/UVC 输入：

```text
/dev/videoX -> V4L2 mmap -> MJPG 1280x480 -> producer callback
```

最小配置：

```text
device: /dev/video0 或自动发现
width: 1280
height: 480
fps: 30
pixelformat: MJPG
io_method: mmap
```

建议新增目录：

```text
stream-sever/src/media_producer/uvc/
├── uvc_config.h
├── uvc_producer.h
├── uvc_producer.cpp
└── CMakeLists.txt
```

建议配置结构：

```cpp
struct UvcConfig {
    std::string device = "/dev/video0";
    int width = 1280;
    int height = 480;
    int fps = 30;
    uint32_t pixelformat = V4L2_PIX_FMT_MJPEG;
    int buffer_count = 4;
};
```

## 自动发现摄像头节点

不要固定 `/dev/video0`。建议扫描 `/sys/class/video4linux/video*/name`：

```bash
for n in /sys/class/video4linux/video*/name; do
  echo -n "$n: "
  cat "$n"
done
```

USB 摄像头节点名称类似：

```text
/sys/class/video4linux/video0/name: USB Camera: USB Camera
```

程序中应：

1. 遍历 `/dev/video*`
2. 查询 `VIDIOC_QUERYCAP`
3. 筛选 `driver == "uvcvideo"`
4. 筛选能力包含 `V4L2_CAP_VIDEO_CAPTURE`
5. 枚举格式，确认支持 `MJPG 1280x480`
6. 选择第一个符合条件的节点

## V4L2 采集流程

UVC Producer 推荐流程：

```text
open("/dev/videoX")
VIDIOC_QUERYCAP
VIDIOC_ENUM_FMT / VIDIOC_ENUM_FRAMESIZES / VIDIOC_ENUM_FRAMEINTERVALS
VIDIOC_S_FMT: 1280x480 MJPG
VIDIOC_S_PARM: 30fps
VIDIOC_REQBUFS: mmap buffers
VIDIOC_QUERYBUF + mmap
VIDIOC_QBUF
VIDIOC_STREAMON
loop:
  poll/select
  VIDIOC_DQBUF
  copy MJPG frame
  callback(frame)
  VIDIOC_QBUF
VIDIOC_STREAMOFF
munmap
close
```

## 和现有分发链路的关系

当前 RTSP/WebRTC/WS/File 大多围绕 H.264 Annex-B 编码流设计，类型为：

```cpp
EncodedStreamPtr = std::shared_ptr<VENC_STREAM_S>;
```

而 UVC MJPG 帧不是 `VENC_STREAM_S`。因此有两条路线：

### 路线 A：快速预览/算法输入

新增 MJPG/JPEG 帧分发接口，仅给 PyQt/算法端使用：

```text
UVC Producer -> MJPG frame -> HTTP/WebSocket/自定义 TCP -> PyQt
```

优点：

```text
实现快
CPU 压力低
直接使用摄像头 MJPG 输出
```

缺点：

```text
不能直接复用现有 H.264 RTSP/WebRTC/MP4
```

### 路线 B：完整接入现有推流系统

将 MJPG 解码为 YUV/NV12，再送入编码器生成 H.264：

```text
UVC MJPG -> JPEG decode -> NV12 -> RKMPI VENC -> H.264 -> RTSP/WebRTC/MP4
```

优点：

```text
复用现有 RTSP/WebRTC/WS/File 分发
```

缺点：

```text
需要 JPEG 解码和像素格式转换
实现复杂度高
需要评估 RV1106 CPU/硬件解码能力
```

当前已按路线 B 完成首版链路：UVC MJPG 经 FFmpeg 软件解码、NV12 转换和 RKMPI VENC 后，复用 RTSP、WebRTC、WebSocket Preview 和 MP4 分发。路线 A 已取消，PyQt 推理暂不在当前阶段处理。
