# 双目相机图像采集开发文档

本文档记录当前 Luckfox Pico Ultra W + USB UVC 双目相机的图像采集方案、板端验证命令和后续接入 `stream-server` 的开发路线。

## 当前硬件结论

当前双目相机不是 MIPI CSI 传感器，而是 USB 2.0 UVC 摄像头。

相机规格：

```text
型号: HBVCAM-4M2214HD-2 V11
接口: USB 2.0
驱动: Linux UVC / uvcvideo
输出格式: MJPG / YUYV
推荐采集: MJPG 1280x480 30fps
备用采集: YUYV 1280x480 10fps
```

板卡规格：

```text
板卡: Luckfox Pico Ultra W
系统: Linux 5.10.160
USB 摄像头节点: 不固定，需运行时识别
```

注意：Luckfox Pico Ultra / Ultra W 的 USB-A 和 USB-C 不能同时作为 USB 数据通道使用。

```text
USB-C 有供电  -> USB 通道切到 USB-C
USB-C 无供电  -> USB 通道切到 USB-A
```

因此使用 USB-A 外接摄像头时，不能用 USB-C 给板子供电。需要使用外部 5V 供电、POE 模块或其它独立供电方式。

## 图像数据形态

该双目相机输出的是左右拼接图像：

```text
1280x480 = 左目 640x480 + 右目 640x480
```

客户端或算法侧可以按宽度中线拆分：

```text
left  = frame[:, 0:640]
right = frame[:, 640:1280]
```

如果使用 `3840x1520`：

```text
left  = frame[:, 0:1920]
right = frame[:, 1920:3840]
```

## stream-server 当前状态

当前 `stream-server/src` 同时支持 SimpleIPC 和 UVC H.264 两条 producer 链路：

```text
SimpleIPC: VI -> VPSS -> VENC -> H.264 stream
UVC: /dev/videoX -> MJPEG -> FFmpeg decode -> swscale NV12 -> VENC -> H.264 stream
```

UVC 模式已能通过 `start_app.sh --mode uvc` 启动，并复用现有 RTSP、WebRTC、WebSocket Preview 和 File 分发链路。当前功能链路已通过板端验收，后续主要问题是软件 MJPEG 解码和像素转换导致的帧率瓶颈。

## UVC Producer 开发目标

目标是在 `stream-server/src/media_producer/` 下新增 V4L2/UVC 输入：

```text
/dev/videoX -> V4L2 mmap -> MJPG 1280x480 -> producer callback
```

最小配置：

```text
device: /dev/video0 或自动发现
width: 1280
height: 480
fps: 30
pixelformat: MJPG
io_method: mmap
```

建议新增目录：

```text
stream-server/src/media_producer/uvc/
├── uvc_config.h
├── uvc_producer.h
├── uvc_producer.cpp
└── CMakeLists.txt
```

建议配置结构：

```cpp
struct UvcConfig {
    std::string device = "/dev/video0";
    int width = 1280;
    int height = 480;
    int fps = 30;
    uint32_t pixelformat = V4L2_PIX_FMT_MJPEG;
    int buffer_count = 4;
};
```

## 自动发现摄像头节点

不要固定 `/dev/video0`。建议扫描 `/sys/class/video4linux/video*/name`：

```bash
for n in /sys/class/video4linux/video*/name; do
  echo -n "$n: "
  cat "$n"
done
```

USB 摄像头节点名称类似：

```text
/sys/class/video4linux/video0/name: USB Camera: USB Camera
```

程序中应：

1. 遍历 `/dev/video*`
2. 查询 `VIDIOC_QUERYCAP`
3. 筛选 `driver == "uvcvideo"`
4. 筛选能力包含 `V4L2_CAP_VIDEO_CAPTURE`
5. 枚举格式，确认支持 `MJPG 1280x480`
6. 选择第一个符合条件的节点

## V4L2 采集流程

UVC Producer 推荐流程：

```text
open("/dev/videoX")
VIDIOC_QUERYCAP
VIDIOC_ENUM_FMT / VIDIOC_ENUM_FRAMESIZES / VIDIOC_ENUM_FRAMEINTERVALS
VIDIOC_S_FMT: 1280x480 MJPG
VIDIOC_S_PARM: 30fps
VIDIOC_REQBUFS: mmap buffers
VIDIOC_QUERYBUF + mmap
VIDIOC_QBUF
VIDIOC_STREAMON
loop:
  poll/select
  VIDIOC_DQBUF
  copy MJPG frame
  VIDIOC_QBUF
  callback(frame)
VIDIOC_STREAMOFF
munmap
close
```

## 和现有分发链路的关系

当前 RTSP/WebRTC/WS/File 大多围绕 H.264 Annex-B 编码流设计，类型为：

```cpp
EncodedStreamPtr = std::shared_ptr<VENC_STREAM_S>;
```

而 UVC MJPG 帧不是 `VENC_STREAM_S`。因此有两条路线：

### 路线 A：快速预览/算法输入

新增 MJPG/JPEG 帧分发接口，仅给 PyQt/算法端使用：

```text
UVC Producer -> MJPG frame -> HTTP/WebSocket/自定义 TCP -> PyQt
```

优点：

```text
实现快
CPU 压力低
直接使用摄像头 MJPG 输出
```

缺点：

```text
不能直接复用现有 H.264 RTSP/WebRTC/MP4
```

### 路线 B：完整接入现有推流系统

将 MJPG 解码为 YUV/NV12，再送入编码器生成 H.264：

```text
UVC MJPG -> JPEG decode -> NV12 -> RKMPI VENC -> H.264 -> RTSP/WebRTC/MP4
```

优点：

```text
复用现有 RTSP/WebRTC/WS/File 分发
```

缺点：

```text
需要 JPEG 解码和像素格式转换
实现复杂度高
需要评估 RV1106 CPU/硬件解码能力
```

当前已按路线 B 完成首版链路：UVC MJPG 经 FFmpeg 软件解码、NV12 转换和 RKMPI VENC 后，复用 RTSP、WebRTC、WebSocket Preview 和 MP4 分发。路线 A 已取消，PyQt 推理暂不在当前阶段处理。

## 帧率瓶颈分析与优化方案

### 现象与结论

当前 WebSocket H.264 预览稳定在约 `13~14fps`，低于相机配置的 `MJPG 1280x480 30fps`。已有实测数据如下：

- 纯 V4L2 MJPEG 采集 300 帧耗时约 10.32 秒，实际约 `29.1fps`。
- 加入 FFmpeg software MJPEG decode、swscale NV12 和 RKMPI VENC 后，完整输出约 `14fps`。
- Web 页面实测约 `13fps`，与板端完整转码链路的已知性能边界一致。

因此，相机、USB 2.0 输入和 V4L2 mmap 采集已能接近 30fps，当前首要瓶颈是板端串行执行的软件 MJPEG 解码与 NV12 转换，不是 RTSP、WebSocket 或浏览器网络带宽。

### 当前数据流和阻塞点

```text
UVC MJPEG 30fps
  -> V4L2 DQBUF
  -> copy owned MJPEG frame
  -> V4L2 QBUF
  -> FFmpeg MJPEG software decode
  -> swscale to NV12
  -> RKMPI MB cache flush
  -> RK_MPI_VENC_SendFrame
  -> EncodedStreamDispatcher
  -> RTSP / WebRTC / WebSocket Preview / File
```

`UvcProducer::CaptureLoop()` 将 owned MJPEG frame 同步交给 `UvcH264Producer::EncodeFrame()`。回调内会连续完成 JPEG 解码、`sws_scale`、MB 获取、cache flush 和 VENC 送帧；当前帧处理未结束前，采集线程不会继续 DQBUF。

`14fps` 意味着完整处理时间约为：

```text
1000ms / 14fps = 71ms/frame
```

而 `30fps` 的时间预算只有：

```text
1000ms / 30fps = 33ms/frame
```

因此完整转码链路至少需要提升约 `2.1` 倍，考虑运行抖动后应以 `2.5` 倍左右的性能余量为目标。采集线程被阻塞期间，相机仍然在产生帧；V4L2 buffer 填满后会出现 sequence 跳号和驱动丢帧，输出帧率最终受限于转码速度。

### Web 页面 FPS 的统计语义

WebSocket Preview 页面中的 FPS 是每秒收到的 WebSocket binary message 数，不是浏览器实际呈现的帧数。服务端稳定运行时基本每个 VENC 输出帧发送一条 WebSocket 消息，因此该数值可以近似反映 H.264 输出帧率；新建连接时单独发送 SPS/PPS，会造成短暂的统计偏差。

JMuxer 当前配置的 `fps: 30` 不会把 13fps 的输入变成 30fps，也不是板端产帧不足的原因。后续若需区分“编码输出帧率”与“浏览器呈现帧率”，浏览器端应增加 `requestVideoFrameCallback` 或 `getVideoPlaybackQuality()` 统计。

### 优化目标和边界

性能优化的目标是：

- 在 `MJPG 1280x480 30fps` 输入下，稳定输出接近 30fps 的 H.264。
- 采集阶段不被 JPEG decode/VENC 长时间阻塞。
- 队列积压时主动丢弃旧帧，优先保证实时性，不累积数秒级延迟。
- 保持 `IMediaProducer` 输出 H.264 `EncodedStreamPtr` 的现有语义。
- 保持 `StreamManager` 作为 RTSP、WebRTC、WebSocket Preview 和 File service 的唯一所有权边界。
- distribution 层不感知输入来自 SimpleIPC 还是 UVC，HTTP path、status code、message 和现有 JSON 字段保持兼容。
- 只局部替换 `UvcH264Producer` 内部解码/转换实现，不改变 producer/distribution 分层。

### 阶段 1：增加分段性能统计

在改变数据流前，先增加低频汇总日志，至少记录：

- V4L2 DQBUF 实际帧率。
- `v4l2_buffer.sequence` 跳号数量和估算驱动丢帧数。
- owned MJPEG 帧拷贝耗时。
- FFmpeg `avcodec_send_packet/receive_frame` 解码耗时。
- `sws_scale` 转为 NV12 的耗时。
- RKMPI MB 获取、cache flush 和 `RK_MPI_VENC_SendFrame` 耗时。
- VENC H.264 dispatcher 实际输出帧率。
- 后续队列的深度、主动丢帧数和最大等待时间。

日志应每 100 帧或固定时间汇总一次，不得每帧输出 INFO 日志而反向干扰性能。本阶段成功标准是能明确区分 decode、swscale 和 VENC send 各自占用的时间，并证明帧丢在哪个边界发生。

### 阶段 2：解耦采集与转码

将采集线程的职责收窄为：

```text
DQBUF -> copy owned MJPEG -> QBUF -> push bounded latest-frame queue
```

由 `UvcH264Producer` 管理的独立处理线程执行：

```text
pop MJPEG -> decode -> NV12 -> VENC_SendFrame
```

队列建议容量为 1~2 帧。队列已满时丢弃旧帧并保留最新帧，同时记录 drop counter。不使用无上限队列，不通过积压历史帧换取表面上的不丢帧。

该阶段能使 V4L2 采集保持接近 30fps，也能防止播放数秒前的旧帧，但如果软件解码仍然只有 14fps，最终 H.264 输出仍只有约 14fps。因此解耦是延迟和结构优化，不是达到 30fps 的充分条件。

### 阶段 3：验证 RKMPI JPEG/MJPEG 硬件解码

当前 SDK 头文件已提供 MJPEG/JPEG 解码相关类型和 API，包括：

```text
MPP_VIDEO_CodingMJPEG
RK_MPI_VDEC_CreateChn
RK_MPI_VDEC_StartRecvStream
RK_MPI_VDEC_SendStream
RK_MPI_VDEC_GetFrame
RK_MPI_VDEC_ReleaseFrame
```

头文件存在不等于当前 RV1106 固件、驱动和 RKMPI 动态库组合已经能正确解码这台相机的 MJPEG。在替换正式 producer 前，应先建立独立板端 probe，不接入 RTSP/WebRTC/WebSocket。

probe 至少验证：

- 连续解码 300 帧真实 UVC MJPEG，无持续解码错误。
- 实际解码速度可稳定支持 30fps，并留有一定余量。
- 输出帧的 pixel format、width/height、virtual width/height 和 stride。
- 输出颜色、左右拼接方向和 JPEG full-range/BT.601 转换是否正确。
- `SendStream/GetFrame/ReleaseFrame` 的 timeout、异常帧和 shutdown 行为。
- 反复创建、启动、停止和销毁 VDEC channel 无资源泄漏。

### 阶段 4：将硬件解码接入 UvcH264Producer

若独立 probe 通过，将正式数据流替换为：

```text
/dev/videoX
  -> UvcProducer owned MJPEG frame
  -> RKMPI VDEC/JPEG
  -> NV12 VIDEO_FRAME_INFO_S
  -> RKMPI VENC H.264
  -> EncodedStreamDispatcher
  -> existing consumers
```

优先验证 VDEC 输出的 NV12 frame 能否直接作为 VENC 输入。若 pixel format、stride、MB 所有权和 channel 约束允许，再评估 VDEC -> VENC bind 或 MB 复用，以去掉 CPU `sws_scale`、整帧 NV12 写入和额外 cache flush。

不应在没有实机证据前直接实现 bind。首先采用明确的 `SendStream -> GetFrame -> SendFrame -> ReleaseFrame` 路径验证正确性，再单独优化 zero-copy/bind，避免同时引入 decoder 替换、资源所有权和 channel bind 三类变量。

### 软件优化备选

如果板端 RKMPI VDEC 不支持该 MJPEG 码流，再评估软件路线：

- 对比 Debug 和 Release 构建，但不预设单纯改为 Release 就能从 14fps 提升到 30fps；主要耗时位于预编译 FFmpeg/libswscale 时，主程序编译优化的收益有限。
- 确认板端 FFmpeg/libswscale 是否启用 ARM/NEON 优化。
- 评估 libjpeg-turbo 及直接 YUV plane 输出，减少中间 RGB/YUV 转换。
- 只在 CPU 核数和实测允许时评估多 decoder context 并行；单纯设置更大的 FFmpeg `thread_count` 不保证单帧 JPEG 解码能按比例加速。
- 如果必须使用多帧并行，每个 worker 必须拥有独立 decoder context，并明确输出顺序和 latest-frame drop 策略。

相机的 `YUYV 1280x480` 仅支持约 10fps，不能通过改用该格式实现完整双目 30fps。`YUYV 640x480 30fps` 会失去当前 `1280x480` 左右拼接的完整分辨率，也不作为首选方案。

### 建议实施顺序

```text
1. 分段计时和 sequence/drop 统计
2. 采集/转码解耦，bounded latest-frame queue
3. RKMPI MJPEG VDEC 独立板端 probe
4. 用 VDEC 替换 FFmpeg decode + swscale
5. 验证 VDEC frame 直接送 VENC
6. 有实机证据后再评估 zero-copy 或 VDEC -> VENC bind
7. 最后校正 Web 端源帧率/呈现帧率统计
```

每个阶段必须独立构建和板端验收，用户确认当前阶段测试通过前不进入下一阶段。
